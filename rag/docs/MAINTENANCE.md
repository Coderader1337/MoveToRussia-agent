# Что требует разработчика и с какой частотой

Проект поставлен на паузу как рабочий, но не полностью автономный продукт:
часть операций **не автоматизирована** и требует человека с доступом к коду/VPS.
Ниже — по каждой такой операции: что это, зачем, с какой частотой обычно
требуется, и сложность (нужен ли именно разработчик или достаточно
инструкции).

## Регулярные операции

| Операция | Частота | Кто может сделать | Сложность |
|---|---|---|---|
| Оценка ответов бота (1–10) | каждый запрос | менеджер (это часть UX бота, не поддержка) | — |
| Просмотр `usage_stats.csv` / составление отчёта по качеству | по желанию, раз в 1-2 недели на активной фазе (см. пример — `rag/data/usage_report_*.md`) | владелец продукта, вручную читая CSV или прося ассистента его проанализировать | низкая |
| Обновление `allowed_users.json` (добавить/убрать менеджера) | по мере кадровых изменений (редко) | любой с доступом к серверу/git, правка одного JSON-файла + деплой | низкая |
| Синк Yandex Disk (если используется) | автоматически раз в сутки (таймер) | не требует участия — только если добавляются/меняются офиц. файлы вручную на Yandex Disk | — |

## Операции, требующие разработчика

| Операция | Когда нужна | Что делать | Сложность |
|---|---|---|---|
| **Дозагрузка новой переписки в корпус** | если проект возобновляется и накопилась новая почта менеджеров | перезапустить `export_manager_mailboxes.py` → `clean_thread_quotes.py` → `prepare_rag_corpus.py` → `index_corpus.py` (без `--recreate`, инкрементально) — см. [`DATA_PIPELINE.md`](DATA_PIPELINE.md) | средняя (нужны IMAP-пароли, время на прогон, деньги на DeepSeek если `--distill`) |
| **Пересборка FAQ-каталога** | если появились новые частые вопросы клиентов или разметка `Clients_stats_v4.csv` обновилась | `build_faq_llm.py` (заново или `--merge-only`/`--semantic-only` для части пайплайна) → `index_corpus.py` | средняя-высокая (требует DeepSeek-бюджет, время, проверку результата глазами) |
| **Изменение системного промпта / стиля ответов** | если качество ответов не устраивает, изменились правила компании | правка `mtr_rag/mail_writing_prompt.py` и/или `prompt_data/communication_principles.txt`, обязательный прогон `smoke_test.py`, желательно — ручное тестирование на dev-боте перед прод | средняя (требует понимания промпт-инжиниринга и контекста бизнеса) |
| **Настройка `top_k` / порогов retrieval** | если ответы нерелевантны (мало/много контекста) | `MTR_RETRIEVAL_TOP_K`, `MTR_DISK_RESERVE_SLOTS`, `MTR_DISK_MIN_SCORE` в `.env`, либо `/topk N` в самом боте (на лету, без деплоя) | низкая (через `/topk`) — средняя (через `.env` + рестарт) |
| **Обновление ключей API (Voyage/DeepSeek/Telegram) при протухании/ротации** | по истечении срока или при компрометации | обновить `.env` на VPS вручную (не через git), `systemctl restart` | низкая, но **обязательно руками на сервере**, не автоматизировано |
| **Ротация/переустановка SSH-ключа деплоя** | если ключ скомпрометирован или сервер меняется | сгенерировать новый ключ, обновить `authorized_keys` на VPS и секрет `RAG_VPS_SSH_KEY` в GitHub — см. [`CICD.md`](CICD.md) и `.cursor/rules/mail-agent.mdc` | средняя |
| **Перенос на новый VPS / восстановление после сбоя сервера** | при смене хостинга или потере сервера | см. [`SETUP.md`](SETUP.md) (с нуля) или [`QDRANT.md`](QDRANT.md) (перенос базы без потери векторов через `clone_qdrant_collection.py`, если старый сервер ещё жив) | высокая — разовая операция, требует внимательности |
| **Диагностика деплоя/CI при сбое** | если GitHub Actions деплой падает | смотреть логи workflow в GitHub Actions, `journalctl -u movetorussia-rag-bot*` на VPS; служебные скрипты `_vps_*.py` в `rag/scripts/` — справочный материал с прошлой настройки, не готовая автоматика | средняя-высокая |
| **Обновление зависимостей** (`requirements.txt`, версия Qdrant в `docker-compose.yml`) | по желанию, нет расписания — проект не настроен на автообновления | обновить версии, прогнать `smoke_test.py`, задеплоить через dev → prod | средняя |
| **Изменение whitelist-логики / прав доступа** | если появится роль кроме "все или ничего" | правка `mtr_rag/whitelist.py`, `bot/middleware.py` | средняя (требует понимания aiogram middleware) |

## Что осталось "на усмотрение" (открытые вопросы, см. также `rag/README.md`)

Эти пункты изначально были обозначены как "оставлено на решение владельца
продукта" — если проект возобновляется, стоит явно решить, менять ли их:

- Значение `top_k` (сейчас 6) и логика приоритизации `low_signal` chunks —
  сейчас просто не исключаются и не бустятся при обычном поиске.
- Формулировка системного промпта — можно донастраивать тон под актуальный
  стиль компании (`mtr_rag/mail_writing_prompt.py`).
- Выбор конкретного FAQ CSV: сейчас `client_faq_review.csv` (224 записи,
  отревьюированные), есть альтернативы `client_faq_frequent.csv`
  (только частые) — переключается через `MTR_FAQ_CSV_PATH`.
- Возможная интеграция `index_corpus.py` в n8n cloud как шаг инкрементальной
  догрузки писем (упоминалось как идея, не реализовано).

## Что НЕ требует разработчика (можно делегировать)

- Ежедневная оценка ответов бота менеджерами — часть обычного использования.
- Добавление .txt-файлов в папку Yandex Disk (`/rag_corpus`) — подхватывается
  автоматически ночным синком, без участия разработчика.
- Чтение/анализ `usage_stats.csv` — обычный CSV, можно открыть в Excel/Sheets.
